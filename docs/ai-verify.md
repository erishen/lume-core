# AI self-verification — "AI writes, machine verifies"

A program generated by an LLM has **no human `.expected` baseline**, so the
core cannot judge it by "matches the golden output". The gate judges
**backend equivalence** instead: if the interpreter, the hand-written
IR-text emitter and the libLLVM emitter all run the program to the same
byte-for-byte stdout (CRLF-normalized) and no compiler complains, the
program is accepted. This is the machine half of the loop; the LLM half
lives outside the core (see the scope guard below).

## The gate

```
scripts/verify-ai-lume.sh <file.lume> [<file2.lume> ...]
make ai-verify [AI_VERIFY_FILE=path/to/generated.lume]
```

What happens, per file:

1. `--check` — the type checker must accept the program.
2. Run on the interpreter, and on every native backend whose toolchain is
   present (`--compile-text` needs `clang`; `--compile-llvm` needs a build
   with libLLVM). **Any compiler diagnostic rejects** — IR the verifier
   complains about is not "it compiled".
3. At least two legs must have run, then every pair of legs is diffed;
   disagreement rejects the program.
4. If `out/fuzz-driver` exists (`make fuzz-driver`), the file is pushed
   through the parser fuzz path; a crash/hang/leak there rejects it too.

Exit codes: **0** = pass, **1** = reject (the reason — file + first lines of
the failing leg — is written to stderr, ready to log back to the LLM as the
counter-example), **2** = gate could not run (binary missing, or fewer than
two legs available).

## Wiring LLM output in

The gate takes a file; it does not care where the file came from. Three
supported entry points, in increasing order of automation:

- **Interactive**: `scripts/verify-ai-lume.sh gen.lume` — inspect the
  reject reason and hand the counter-example back to the model.
- **Scripted** (external CI or a host tool): run the prompt → `.lume`
  generator, write the result to a temp file, run the gate, and
  - exit 0 → commit the file to `tests/` (it is now a regression seed,
    `make check` + `make fuzz` + `make native-consistency` all cover it);
  - exit 1 → keep the file + the stderr reason as the counter-example and
    re-prompt the LLM for a retry;
  - exit 2 → infrastructure problem, do not blame the program.

  Shipped loop harness (2026-10-21): `scripts/ai-verify-loop.sh` /
  `make ai-verify-loop` assert the expected verdicts over a must-pass set
  (`examples/ai-generated/*.lume`, each must exit 0) and a must-reject
  set (`tests/ai-bad/*.lume`, each must exit 1), and append every
  counter-example to `out/ai-rejects.log` — the ready-made payload to log
  back to the LLM for retry. A producer drops candidates into those
  directories (or overrides `AI_PASS_DIR` / `AI_REJECT_DIR` /
  `AI_REJECTS_LOG`); the loop reads files only. Exit 0 = all verdicts
  held, 1 = a verdict was violated, 2 = the gate could not judge any
  program (toolchain short of two legs). Runs in both CI jobs.
- **GitHub Actions**: the `ai-verify` job in `.github/workflows/ci.yml`
  runs the gate over the shipped seeds (see below) with the libLLVM leg
  live — the leg most local toolchains skip. Point it at a generated file
  with `make ai-verify AI_VERIFY_FILE=...` inside the job, or add the file
  to the seed list.

## Producer — closing "AI writes, machine verifies"

The loop above reads files; the pipeline is only closed when something
*produces* the `.lume` from an LLM reply. The host-side producer is
agent-httpd's tool dispatch — a model writes a program, the host drops it
into a candidates directory. The core ships the deterministic stand-in for
that step plus the produce loop that turns each candidate into an action:

```
make ai-produce                  # scripts/ai-gen-programs.sh + scripts/ai-produce.sh
```

- `scripts/ai-gen-programs.sh` — a scripted "prompt → .lume" generator: a
  list of program intents (the prompts) and one template candidate per
  intent, written to `out/ai-candidates/` (override `AI_CANDIDATES_DIR`)
  together with a manifest:
  `name|expected (accept|reject)|prompt`. Six candidates are accept-class
  (plausible LLM programs on the native backends' covered surface); one,
  `gen-bad-untyped-tdist`, is deliberately reject-class — `let p =
  tdist_cdf(...)` missing the `let p: float` annotation the native
  backends need (the statistical builtins are not in their inference
  tables), which is exactly the counter-example the gate teaches the LLM
  with.
- `scripts/ai-produce.sh` — runs every candidate through the gate and
  asserts the manifest verdict: accept → **READY** (commit the file to
  `tests/`; `make check` + `make fuzz` + `make native-consistency` cover
  it from then on), reject → **counter-example appended to
  `out/ai-rejects.log`** (the payload to log back to the model for retry),
  anything else → verdict violation (exit 1) — a backend drift
  masquerading as a gate pass shows up here, not in a later test run.
  Externally dropped candidates without a manifest row default to accept.
  Exit 0 all verdicts held, 1 a violation, 2 the gate could not judge
  anything. Runs in both CI jobs after `ai-verify-loop`.

The contract for replacing the scripted generator with real host tool
dispatch is just the manifest file: write candidates + manifest rows into
`$AI_CANDIDATES_DIR` and call `scripts/ai-produce.sh`.

**Real dispatch shipped (2026-10-22)** — agent-httpd's
`examples/tools/ai-produce-llm.py` is that host tool: it sends each
prompt to a real LLM (OpenAI-compatible chat completions; config via
`LLM_API_URL` / `LLM_API_KEY` / `LLM_MODEL` — the same names this
repo's `.env` already carries), extracts the ```lume program, runs this
gate locally, and on a rejection loops the counter-example back to the
model for a bounded number of attempts. Accepted programs land in
`$AI_CANDIDATES_DIR` with `accept` manifest rows — exactly the contract
above — so `scripts/ai-produce.sh` gives every LLM candidate a second,
deterministic gate opinion before anything is called READY. The system
spec ships a few-shot reference program: without it a small model
produces Python (`range`/`append`/`while:`), which the gate correctly
rejects and the retry loop feeds back. Two programs produced end to end
by Qwen3-8B through the local router are committed as
`examples/ai-generated/llm-summary-stats.lume` and
`llm-range-sieve.lume` (the must-pass loop covers them from now on).
The key never leaves the environment; the core repo stays key-free and
network-free.

## Seeds kept in the tree

- `examples/ai-generated/norm-stats.lume` — a plausible LLM-generated
  program (statistical builtins, deliberately sloppy shapes) that must
  **pass**.
- `tests/ai-bad/type-mismatch.lume` — LLM-slop that must **reject**
  (string passed for a `float` parameter). Negative fixtures also feed the
  fuzz-driver seed replay, keeping the "rejects what it should" path
  honest.

## Scope guard (TODO P4)

The core interpreter stays host-independent: **no LLM builtin, no network,
no API keys in the core**. The LLM → `.lume` step is host-side —
agent-httpd's tool dispatch or an external CI script — and only the
deterministic verify (this gate) lives in the core. Same boundary as
`server{}`: LLM in, verify out.

## Semantic layer — committed (2026-10-21)

Backend equivalence is *self-consistency*: three legs agreeing says the
program is deterministic and compilable, not that it does what it
claims. `assert_semantic()` — the old open question — is now closed as a
**static declaration contract** enforced by
`scripts/verify-ai-semantics.sh`, which the gate runs before any leg.
The validator never executes the program; it checks the source:
(labels are `[a-z_][a-z0-9_]*` — underscores, not hyphens, so a
hyphenated label like `p-bound` would not match and be silently skipped).

```
//@semantic <label>: <expr>
```

e.g.

```
//@semantic p_bound: 0 < p < 1
//@semantic sorted: the portfolio is sorted ascending
```

Three rules hold a declaration to the program:

1. **Defined** — every identifier the `expr` refers to must be defined in
   the program (`let <name> = ...`, a function parameter, a function
   name). A dangling reference rejects.
2. **Claimed** — at least one `print(...)` must mention the label or one
   of the identifiers it refers to: an invariant the program never
   prints is not being honored.
3. **Safe shape** — the program is a pure computation the host executor
   can run unsupervised: no `server{}` block, no `run()` HTTP bridge.

A program with no declarations passes (empty contract). A rejection
surfaces as the same exit-1 counter-example the gate already returns to
the LLM, so the retry loop teaches the model *why* a declaration dangles
or goes unclaimed. Seeds: `examples/ai-generated/norm-stats.lume` and
`semantic-sort.lume` must pass; `tests/ai-bad/semantic-dangling.lume`
and `semantic-unclaimed.lume` must reject (each for exactly the reason
its name says).

This closes TODO P4's `assert_semantic()` open question. The remaining
"real LLM dispatch" (the host asking an actual model and running the
producer on its reply) is still host-side by the same scope guard; the
core's contract is just the manifest file plus, now, this declaration
language.

## Installed mode — gate as first-class shell commands (2026-10-22)

`install.sh` (and the `make pack` release tarball) ship the gate scripts
next to `lume-core`, so an installed machine verifies AI-written programs
without a checkout:

```
lume-ai-verify <file.lume>              # one program through the full gate
lume-ai-verify-loop                     # assert must-pass / must-reject sets
lume-ai-produce                         # judge producer candidates vs manifest
```

- The scripts resolve `lume-core` from PATH and their own siblings; they
  also run unchanged inside a checkout (repo mode keeps
  `scripts/verify-ai-lume.sh` + `bin/lume-core` defaults).
- `lume-ai-verify-loop` / `lume-ai-produce` default their input dirs to
  checkout-relative paths, so installed use passes them explicitly:
  `AI_PASS_DIR=... AI_REJECT_DIR=... lume-ai-verify-loop`,
  `AI_CANDIDATES_DIR=... lume-ai-produce` (seeds also ship under
  `$PREFIX/share/lume-core/{examples/ai-generated,tests/ai-bad}`).
- The gate compiles its runtime helper objects (rt.c, bridge_native.c and
  the compat regex objects) from source next to `LUME_RT_SRC` on first
  use, so an installed binary — which carries no prebuilt `build/` — runs
  the interp + libLLVM legs as well. `LUME_BIN`, `AI_VERIFY_SH` and
  `AI_SEMANTICS_SH` override the resolution when the layout differs.
- text leg (clang) and parser fuzz leg (`make fuzz-driver`) stay optional;
  the gate still demands at least two legs, exactly as in repo mode.
