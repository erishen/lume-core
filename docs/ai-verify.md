# AI self-verification — "AI writes, machine verifies"

A program generated by an LLM has **no human `.expected` baseline**, so the
core cannot judge it by "matches the golden output". The gate judges
**backend equivalence** instead: if the interpreter, the hand-written
IR-text emitter and the libLLVM emitter all run the program to the same
byte-for-byte stdout (CRLF-normalized) and no compiler complains, the
program is accepted. This is the machine half of the loop; the LLM half
lives outside the core (see the scope guard below).

## The gate

```
scripts/verify-ai-lume.sh <file.lume> [<file2.lume> ...]
make ai-verify [AI_VERIFY_FILE=path/to/generated.lume]
```

What happens, per file:

1. `--check` — the type checker must accept the program.
2. Run on the interpreter, and on every native backend whose toolchain is
   present (`--compile-text` needs `clang`; `--compile-llvm` needs a build
   with libLLVM). **Any compiler diagnostic rejects** — IR the verifier
   complains about is not "it compiled".
3. At least two legs must have run, then every pair of legs is diffed;
   disagreement rejects the program.
4. If `out/fuzz-driver` exists (`make fuzz-driver`), the file is pushed
   through the parser fuzz path; a crash/hang/leak there rejects it too.

Exit codes: **0** = pass, **1** = reject (the reason — file + first lines of
the failing leg — is written to stderr, ready to log back to the LLM as the
counter-example), **2** = gate could not run (binary missing, or fewer than
two legs available).

## Wiring LLM output in

The gate takes a file; it does not care where the file came from. Three
supported entry points, in increasing order of automation:

- **Interactive**: `scripts/verify-ai-lume.sh gen.lume` — inspect the
  reject reason and hand the counter-example back to the model.
- **Scripted** (external CI or a host tool): run the prompt → `.lume`
  generator, write the result to a temp file, run the gate, and
  - exit 0 → commit the file to `tests/` (it is now a regression seed,
    `make check` + `make fuzz` + `make native-consistency` all cover it);
  - exit 1 → keep the file + the stderr reason as the counter-example and
    re-prompt the LLM for a retry;
  - exit 2 → infrastructure problem, do not blame the program.
- **GitHub Actions**: the `ai-verify` job in `.github/workflows/ci.yml`
  runs the gate over the shipped seeds (see below) with the libLLVM leg
  live — the leg most local toolchains skip. Point it at a generated file
  with `make ai-verify AI_VERIFY_FILE=...` inside the job, or add the file
  to the seed list.

## Seeds kept in the tree

- `examples/ai-generated/norm-stats.lume` — a plausible LLM-generated
  program (statistical builtins, deliberately sloppy shapes) that must
  **pass**.
- `tests/ai-bad/type-mismatch.lume` — LLM-slop that must **reject**
  (string passed for a `float` parameter). Negative fixtures also feed the
  fuzz-driver seed replay, keeping the "rejects what it should" path
  honest.

## Scope guard (TODO P4)

The core interpreter stays host-independent: **no LLM builtin, no network,
no API keys in the core**. The LLM → `.lume` step is host-side —
agent-httpd's tool dispatch or an external CI script — and only the
deterministic verify (this gate) lives in the core. Same boundary as
`server{}`: LLM in, verify out.

`assert_semantic()` (declaring invariants in the program that a host-side
validator checks without running it) remains an **uncommitted open
question** — deliberately not part of this gate.
